API contracts and versions

Start with the pinned k8s.io/api, apimachinery and client-go versions in go.mod. A current web page is not proof an older server supports a field or API. Use Context7 as required by repository instructions for current API/library questions; retain the supporting official URL and version context in the task's spec or validation notes. Re-check references when dependencies or supported servers change; do not upgrade dependencies just to match an example.

  • API concepts: discovery, resourceVersion, pagination, continuation, watch and expired resource versions. An empty filtered page alone is not end-of-list.
  • client-go compatibility and versioning: select documentation appropriate to the pinned client and tested server, not an assumed universal compatibility claim.
  • Kubernetes API reference: exact groups, versions, resource scope, fields and subresources. Verify empty-namespace behavior before routing cluster-scoped resources through namespaced helpers.
  • RBAC authorization: resource versus subresource verbs and namespace versus cluster scope. Permission denial is not evidence of an empty collection.
  • Official client-go examples: usage patterns only. Inspect pinned APIs and existing KubeSift abstractions before adapting example code.

Identity and relationships

  • Owners and dependents: ownerReferences, UIDs and scope restrictions. Compare with workload ownership/navigation decisions.
  • Object names and UIDs: distinguish a name lookup from identity preserved across deletion and recreation.
  • Labels and selectors: use selector syntax correctly; label association is distinct from ownerReference evidence.
  • Networking reference contract: allowlisted name references, captured source identity/version, label-associated slices and cluster-scoped IngressClass. This is the product decision, not a general Kubernetes guarantee.

Network policy NetworkPolicies Selector grouping, policyTypes, empty rules and additive policies; configuration is not proof of CNI enforcement.
Events and serialization Event API, evidence design UID scoping, optional times/counts, retention, page ordering and API-family fallback. Typed serialization does not preserve arbitrary unknown fields or original manifest formatting.

Namespace policy and configuration

  • Metadata-only API negotiation: partial metadata representation, unsupported negotiation and explicit full-object fallback. The 1C.3c contract forbids that fallback for Secrets.
  • LimitRange API: item types, quantities, defaults and constraints; keep multiple items distinct.
  • ConfigMap API: text/binary data and immutable configuration; values can be sensitive despite the resource kind.
  • ResourceQuota allocation example: configured limits and reported accounting are not measured CPU/memory consumption.

Testing and evidence

  • client-go fake testing scope and limitations: use fake clients for deterministic request/error/identity logic; they do not substitute for the API server and controllers.
  • Official fake-client example: adapt to existing tests; do not infer live RBAC, defaulting or reconciliation from a fake pass.
  • Local development fixtures and owned inventory: select existing synthetic cases and approved explicit contexts before creating test data.
  • Integration entry points: opt-in real API behavior and two-cluster isolation. Inspect the current test files and environment contract; this index does not start tests or create clusters.
  • Packaged-app desktop verification: agent-run user journeys, clipboard/keyboard/layout/native behavior and one report of passed, failed and unrun checks. No duplicate manual user UAT by default.

Common evidence mistakes: treating a fake list as proof of server pagination, a browser screenshot as proof of native behavior, a status counter as proof of connectivity, or a current name lookup as proof of the original object's UID. Choose the test layer that can actually falsify the claim and keep remaining limitations explicit.
