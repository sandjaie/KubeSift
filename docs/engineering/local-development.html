Local development

Two kind clusters · 2026-11-06

Development clusters

kind-dev-local-a and kind-dev-local-b are the only clusters for day-to-day development. They are merged into the default kubeconfig, so a blank kubeconfig path in the app lists both contexts. Do not create another cluster for routine development, and do not use any other context in this kubeconfig for KubeSift work.

Context Namespace What you should see
kind-dev-local-a shop Deployments web-frontend and cart-api, two replicas each. Services with the same names. ConfigMaps web-settings and catalog-copy. Secrets web-tls and cart-db. DaemonSet node-log-agent. Ingresses storefront and cart. One control-plane node.
kind-dev-local-b billing Deployments invoice-api and ledger-worker, two replicas each. Services with the same names. ConfigMaps invoice-settings and tax-rates. Secrets billing-db and payment-token. DaemonSet metric-agent. Ingresses invoices and ledger. One control-plane node.

Workloads run registry.k8s.io/pause:3.10 with tiny CPU and memory requests. Ingress objects are the routes; no ingress controller is installed, so they have no external address. Secret values are fake local placeholders. Pod names gain a rollout suffix; read them from the cluster instead of hardcoding them. 

kubectl --context kind-dev-local-a -n shop get deploy,ds,svc,cm,secret,ingress,pods
kubectl --context kind-dev-local-b -n billing get deploy,ds,svc,cm,secret,ingress,pods
kubectl --context kind-dev-local-a get nodes

Agent actions

Agents may get, describe, log, exec, apply, create, and delete resources in these two clusters when the work requires it. Every call passes --context and, for a namespaced resource, the namespace. Do not rely on the current context. Do not read or change any other context, including shared or production contexts in the same kubeconfig. Do not delete dev-local-a or dev-local-b unless the user asks.

Resume

scripts/dev-clusters.sh creates dev-local-a and dev-local-b when either is absent, then applies the sample workloads embedded in the script. Each new cluster has one control-plane node and the pinned kind node image. Missing Docker, kind, or kubectl stops the script. Running it again applies the workloads and does not delete the clusters. It restores the previous current context when that context still exists.

Phase 1A fixtures

scripts/local-clusters.sh remains the opt-in Phase 1A fixture tool. It is not the development cluster setup, and it still expects the historical kind-dev-local and kind-kubesift-b names recorded by that validation. Do not use it in place of scripts/dev-clusters.sh.
