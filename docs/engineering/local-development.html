Local development and validation

User-provided target · 2026-11-05

Review clusters

These three kind clusters are the shared local environment. They are merged into the default kubeconfig, so a blank kubeconfig path in the app lists their contexts. Agents use these contexts and namespaces. Do not create another cluster for routine development.

kind-dev-localpayments, app-stgcheckout-api crashes because DATABASE_URL is missing. payments-db and web-ui run.
kind-dev-healthyshopstorefront runs.
kind-dev-brokenincidentscheckout-api crashes with the same missing-setting log. missing-image stays in ImagePullBackOff.

Discover current Pod names rather than hardcoding rollout suffixes. Check status and events first. Running-container log and exec checks wait for the relevant container or report why they cannot run.

kubectl --context kind-dev-local -n payments get pods
kubectl --context kind-dev-local -n payments get events --sort-by=.metadata.creationTimestamp

Ownership and cleanup

Treat dev-local, dev-healthy, and dev-broken as user-owned. Do not delete or recreate them, reset their namespaces, or rerun the setup script as part of test setup. Track validation-created resources by run ownership and clean up only those resources. Put mutation checks on a dedicated fixture ConfigMap; use separate named fixture resources when load/log/HTTP behavior is needed. Inspect existing name collisions rather than adopting or replacing resources.

Two-cluster validation

Phase 1A still needs two distinct API servers. Use kind-dev-local as A and a separately managed disposable kind cluster kubesift-b as B, with context kind-kubesift-b. Create matching validation-owned resource names in payments on each, with distinct markers. Record both identities in isolated ignored test configuration. Never treat two contexts for the same API server as two clusters.

Test setup reuses A; it creates B only if absent and records ownership. If B already exists without test ownership, stop setup rather than replace it. Teardown may delete B only if the current run created it; it must never delete A or the payments namespace on A. Fault injection that stops a cluster or container runtime belongs on disposable B; exercise A through cancellable requests or local transport simulation.

Resume

scripts/dev/setup-test-local-cluster.sh creates dev-local, dev-healthy, and dev-broken when each cluster is absent, then applies the committed manifests in scripts/dev/kubesift-dev/. Paths resolve from the repository. New clusters use one control-plane node and the pinned kind node image. Missing Docker, kind, or kubectl stops the script. Re-running applies the manifests and does not delete the clusters. The script does not create kubesift-b. Validation does not call this script. Fixture setup remains scripts/local-clusters.sh up.

Execution boundary

This page records the target for the implementation session. No cluster queries or mutations were performed while writing it. Keep kubeconfig/current-context unchanged. Integration commands must explicitly supply context and namespace; generated test configuration remains outside tracked files. The application installs no supporting infrastructure for its own functionality.
