Engineering playbook

How KubeSift is designed, built, reviewed, and released. Product scope stays in the owning documents.

This page owns the development loop. It does not authorize implementation, cluster access, or publication. Requirements stay in product, boundaries in architecture, safeguards in security, status in decisions, and phase order in the roadmap. The short agent contract is AGENTS.md.

Loop

  1. Design before code. Brainstorm, write a short spec, get a yes. Multi-step work gets a plan with file-level tasks before anyone edits. Planning approval is still not implementation authorization.
  2. Branch off the integration branch. Feature and fix work merges to develop. main moves only through a release or a hotfix.
  3. Test first. Failing test, watch it fail, smallest code that passes.
  4. Stay small. Ponytail lite: build what was asked, then name the lazier option in one line.
  5. Prove it. The gates for the languages you touched run in this session before anyone says it passes. Say which commands ran and which did not.
  6. Review the diff. Correctness review, then hygiene or complexity review when the change is large.
  7. Merge small. Squash-merge, delete the branch.
  8. Release on purpose. Version, changelog, tag, and publish are a skill. They are not a side effect of CI.

Practices

Git

Branching, commits, pull requests, and publication are in gitworkflow.md.

Quality gates

Run these before review, for the code the change touches. A documentation-only change does not start them. A change that crosses the desktop bridge runs both sets. There is no application module yet; these commands start when that module exists.

Go, for services, adapters, sessions, and security:

go test ./...
go vet ./...

React/TypeScript, for presentation:

npx vitest run
npx eslint .
npx tsc --noEmit

Commit runs linters and formatters only. See Hooks. Tests are run by the agent, by scripts/check.sh, and by CI. go vet and tsc --noEmit stay review and pull-request checks.

No coverage threshold. Prettier formats HTML and frontend TypeScript. Frontend lint is ESLint plus typescript-eslint recommended. Go formatting is gofmt, because the Go toolchain owns it. CI runs only for release-producing pull requests into main from release/* or hotfix/* branches. Feature pull requests into develop and all push events do not run CI; agents still run the applicable local checks before publication. Superseded runs are cancelled. Code changes run the Vite production bundle and then scripts/check.sh on Ubuntu. The bundle fills internal/desktop/assets/dist, which the desktop executable embeds and a clean checkout does not contain. Go is compiled with CGO disabled and the purego tag so that package needs neither a macOS runner nor GTK. Bindings generation stays on the local and release checks. TypeScript checking runs once through scripts/check.sh; local npm run build still includes it. Changes confined to docs/, AGENTS.md and root README files run source-description and documentation-link checks in the same check job. Unknown comparison bases receive the full checks. Packaging, signing, notarizing, publishing, and version bumps stay in the release skill.

Authoring and formatting

Write readable, consistently indented code and markup from the first edit, following the surrounding file and repository formatter configuration. Use natural line breaks; do not deliberately write compact or minified source for a formatter to expand later. Aim to match the configured style without spending time manually reproducing every formatter wrapping rule.

After editing, normalize only the changed files with the applicable repository tools: Prettier for HTML and frontend TypeScript, ESLint for frontend lint fixes, and gofmt for Go. Review the resulting diff and avoid unrelated formatting churn. Keep the commit hooks as the final safeguard; they do not replace readable authoring.

Hooks

Husky installs the commit hook on npm install via the prepare script. There is no push hook.

pre-commit — .husky/pre-commit runs npx lint-staged.

lint-staged looks only at files already staged for this commit. For *.html it runs prettier --write with print width 140. For *.ts and *.tsx it runs prettier --write, then eslint --fix. For *.go it runs gofmt -w. Other files are left alone. When a fixer rewrites a file, lint-staged puts that rewrite back into the index, so the commit contains the fixed code. A remaining lint error aborts the commit.

This is the fast check. It does not lint the rest of the working tree, it does not typecheck, and it does not run tests. A commit of markdown, YAML, or JSON does not start ESLint, gofmt, or Prettier.

What the hook does not do

  • No tests on commit or push. The agent runs the tests the change needs. scripts/check.sh and CI still run the Go and frontend suites.
  • No commit-msg hook. Conventional Commits are the agreed style. Git will not reject a message that breaks it.
  • No go vet and no tsc --noEmit. Those run before review, and they are checkboxes on the pull request template.
  • No coverage gate. Fixture and credential-handling requirements are review rules. See the security model.

On release-producing pull requests, CI runs lint and the unit suites again. Skipping a hook with --no-verify does not skip the pipeline. Use --no-verify only when you mean to, and say so.

No automated native Wails UI end-to-end suite is planned for Phase 1A. Use unit tests with injected clients/session fakes, explicit opt-in local-cluster integration tests, and a recorded packaged-app smoke test. These are complementary checks; mocks alone do not establish integration correctness. Mutation checks use a disposable local cluster. External contexts require an explicit context, namespace and allowed actions.

Tests

Keep tests minimal and behavior-focused: representative checks for trust boundaries, targeting, cancellation and data-loss risks. Avoid exhaustive UI suites, snapshots and tests that mirror implementation. Use one opt-in local integration scenario and a short agent-executed packaged-app verification where appropriate. Add regression tests when a real defect justifies them.

  • Go tests live in *_test.go beside the package they lock. Frontend tests are Vitest, next to the behavior they lock. Exact trees are fixed when the source layout is created.
  • Write the test before the production code. If you did not see it fail, it does not count.
  • Unit tests use synthetic fixtures. They do not talk to a live cluster or a live git remote.
  • A milestone that needs a cluster uses a disposable local cluster and names the tool. The app installs nothing into that cluster for its own functionality.
  • A bug fix gets a regression test at the shared function, after every caller has been traced.

Agent verification and acceptance

The implementing agent owns post-implementation verification: run meaningful automated checks and use desktop computer-use tools to verify the affected workflows in the packaged application. Record one validation report with the tested build, environment, explicit local contexts, evidence, and passed, failed or unrun checks. Label agent observations honestly; they do not mean the user personally tested the application. Browser checks alone do not establish native desktop behavior.

Do not create or require a separate manual user UAT checklist by default, or ask the user to repeat workflows already verified by the agent. Ask for user input only for subjective design decisions or specific checks the agent cannot complete; explain the limitation and the precise input needed. Keep unrun or blocked checks visible and agent-owned where feasible. Failed checks and material verification gaps remain unresolved until fixed, verified or explicitly accepted with their limitations.

This policy was requested on 13 November 2026 and supersedes duplicate manual-user-UAT requirements in earlier specs, plans, status notes and checklists. Existing user checklists are optional historical records, not automatic acceptance or merge blockers. Preserve their actual outcomes; never convert Not tested into Passed. Independent code review, required technical checks, release smoke tests and explicit merge/release authorization rules remain in force.

Project layout and source descriptions

cmd/kubesift owns the executable entry point; internal owns Go services and the thin desktop adapter; frontend/src owns React presentation; build owns desktop build and packaging support; scripts owns checks and development tooling; tests owns synthetic fixtures and opt-in integration. Root go.mod/go.sum define the module. The tiny root Taskfile.yml lets Wails discover tasks and delegates to build/Taskfile.yml.

Every project-owned Go, TS and TSX file has a plain-English header with Purpose, Used by, Responsibilities and relevant Important notes. Describe actual behavior and callers, including safety boundaries where relevant. Keep handwritten descriptions with their source. The binding task annotates generated glue after regeneration; do not edit generated RPC code.

Start at the planning index for durable status. For a portable resume checkpoint, read tracked .superpowers/sdd/status.md, then the local active plan ledger if present. A fresh clone uses the permanent plan and phase validation report. Update local status only after verification.

Keep permanent implementation plans current: change each completed step from [ ] to [x] immediately after its required verification succeeds, in the same work session. Check off a task only when all its required steps are complete. Leave pending or blocked checks unchecked and explain their status; an execution ledger alone is not a substitute for updating the plan. Commit these checkbox updates with the related work so another laptop can resume accurately.

Documentation layout

docs/index.html is the documentation entry point. Product, architecture, security, UX, roadmap and engineering directories own durable project documentation. Reusable build and toolchain instructions belong in engineering/toolchain.html.

  • docs/superpowers/specs/: approved specifications.
  • docs/status.md: entry point to the tracked SDD checkpoint, plan checkboxes and validation reports. The roadmap owns scope, order, dependencies and exit criteria only; never record implementation progress or merge/test status there.
  • docs/superpowers/plans/: detailed execution plans.
  • docs/superpowers/validation/: phase acceptance reports and summarized measurements.
  • docs/superpowers/evidence/<phase>/: only curated, synthetic raw proof needed to audit a permanent phase result. Keep a short manifest explaining each retained file.
  • .superpowers/sdd/: ignored local execution ledgers, progress, checks, diffs, logs, reviews, handoffs, working notes and temporary Markdown. The concise status.md checkpoint is tracked for resuming on another machine; it links permanent plans and reports and contains no machine-local evidence. Archive generated operational outputs here after each run.

Permanent reports summarize scope, methods, results, limitations and accepted history, with links to curated proof when raw values matter. Operational history remains in local SDD; do not copy it into public evidence. Specs and plans stay permanent so fresh clones can understand the work. Test fixtures stay in tests/. Runtime credentials, ownership records and live app output remain in ignored .local/ under the security model. Never commit credentials or generated kubeconfigs. Update public links when moving documents.

Language and boundaries

  • Go owns Kubernetes clients, operational policy, and session lifecycle. Domain services stay independent of Wails. The desktop adapter translates typed requests and events and holds no business logic.
  • TypeScript is strict and owns presentation: navigation, tables, editors, terminal rendering, confirmations, and transient UI state.
  • Every call carries an explicit connection id, generation, and resource identity. Nothing reads a mutable global current context. The app does not change kubeconfig current-context.
  • Validate KubeSift-owned settings and trust records with strict, versioned schemas; reject unknown keys and unresolved references. Parse kubeconfig using Kubernetes loading semantics and retain supported extensions; validate safety-sensitive fields without rejecting extensible Kubernetes resources. User settings cannot bypass mandatory safety controls. The backend loader is authoritative.
  • Kubeconfig is read-only in Phase 1A. Later YAML editing should preserve user text/comments in the editor and use structured parsing for validation and API requests; server round-trips do not preserve comments or key order. Never use string replacement to mutate Kubernetes resources.
  • One registry is the source of truth for a closed set. Adding a member means extending the registry, the schema, and the tests together. AI providers, when they exist, are one such set.
  • Adapters implement one contract. Specialized OpenShift workflows are a dedicated adapter. Generic discovery stays generic. A new provider is a full adapter.

Security that is part of the design

Safeguards are specified in the security model. These are the engineering consequences.

  • Fail closed. A skipped check is a failed run, unless the user passes an explicit skip that the security model allows.
  • Re-run every safety guard at the moment of the dangerous call. Prepared operations bind connection generation, target, payload, and relevant resource version or UID. Proposed confirmations expire and are single-use. Stale targets require a new review.
  • Never retarget an existing terminal or prepared mutation. Frontend listener removal is not backend cancellation. Reads may reconnect after sleep. Writes and commands must not replay. Do not retry a write whose outcome is uncertain.
  • Clusters the user selects, including ones labeled production, are in scope for an operations client. A production label strengthens confirmation. It does not replace target binding, review, or server authorization.
  • Review a credential helper’s resolved executable, arguments, kubeconfig source, and configured environment overrides before the first run. Prompt again when that configuration changes. Never execute a helper merely to preview an untrusted kubeconfig.
  • Provider keys belong in the OS credential store. Resource caches are memory-only by default. Audit records store action type, target reference, time, outcome, confirmation, and provider profile id. They do not store credentials, full log payloads, or Secret values.
  • Startup readiness is local: commands, paths, and repo shape. Opening a connection is what talks to Kubernetes. Startup does not read tokens to prove the app launched.
  • Use synthetic fixtures and follow the security model for credential handling.
  • Phase 2 AI tools are read-only. Evidence is untrusted data. A missing or invalid provider override fails clearly. There is no silent fallback to another provider, and there are no AI write tools in that phase.
  • KubeSift installs no agent, metrics stack, or other cluster component for its own functionality.

Docs that stay true

  • AGENTS.md is the short contract: what the product is, what must not break, how to test, and what is still planning.
  • Owning HTML documents hold product, architecture, security, decisions, roadmap, UX, and this loop. Specs and plans live under docs/superpowers/specs/ and docs/superpowers/plans/ as YYYY-MM-DD-<name>.md.
  • Update the owning document in the same change as the behavior. Link to it. Do not paste the requirement into a second file.
  • When source exists, every source directory has a hand-maintained README.html, and scripts uses README.md. Update that file in the same change as an add, rename, or delete. Header comments and export docstrings are the module map. Do not generate a second one.
  • A deliberate shortcut that has a known ceiling gets a ponytail: comment naming the ceiling and the upgrade.

Plain-English descriptions in every source file

Every project-owned .go, .ts and .tsx file must begin with a short description of its purpose and consumers. This includes frontend components, hooks, state, backend services, internal packages, desktop adapters, entry points, tests, fixtures, tooling and configuration written in these languages. A reader should understand why the file exists without tracing its code. A directory README does not replace this description.

Use these labels in a normal top-of-file comment. Usually 4–8 short lines are enough; include additional detail only when it helps the reader:

  • Purpose: What this file does for KubeSift, in ordinary language. Explain the user-facing or engineering reason it exists, not just its filename or technical category.
  • Used by: The actual consuming component, package, entry point, test runner or build tool. Name a relevant repository-relative path or symbol when useful. For shared helpers, name the main consumer groups rather than maintaining an exhaustive caller list. For an entry point, explain what launches it.
  • Responsibilities: The important input, output or work it owns. Keep this concrete; do not list every function.
  • Important: Relevant side effects, ownership, cancellation/cleanup, sensitive-data handling, constraints or non-obvious failure behavior. Omit this line if there is nothing useful to add; do not repeat a security checklist in every file.

Example shape for a TypeScript view (adapt names and claims to the actual code):

/**
 * Purpose: Shows the selected Pod's details and available actions.
 * Used by: The workspace screen when the user selects a Pod.
 * Responsibilities: Renders supplied state and forwards user actions to the bridge.
 * Important: Uses the supplied cluster target; it does not choose a global context.
 */

Example shape for a Go session service (describe only behavior the file actually implements):

// Purpose: Keeps track of the live log and terminal sessions opened by the app.
// Used by: Kubernetes adapters and the desktop service that starts and stops sessions.
// Responsibilities: Associates each session with its cluster and exposes cancellation.
// Important: Closing a session must stop its background work and release its resources.

Test files describe the behavior or regression they protect and identify the test runner as their consumer. Configuration files describe which tool reads them. Avoid vague phrases such as “handles logic” or “utility functions”; explain unfamiliar terms when needed. Do not include author names, change histories, stale timestamps, copied function signatures or comments that simply narrate the code.

Keep required language directives, build tags and license notices in their valid positions; place the description immediately after them and before ordinary code. Preserve Go package/exported-symbol documentation and TypeScript API documentation where appropriate; the file description explains the whole file, while symbol comments explain the contract of that symbol.

Generated project files also need a concise purpose/consumer description, their generator/source location, and a clear generated-file marker. Add descriptions through the generator template or a repeatable generation step, not manual edits that disappear on regeneration. Preserve the generator's required markers and directives. Third-party vendored code, installed dependencies and compiled bundles are outside this source-authoring rule.

Update a file's description in the same change when its purpose, consumers or important behavior changes. Verify consumer names against the code. During review, check new and changed files for accurate descriptions; no dedicated test suite or additional documentation framework is required. The implementation agent should backfill existing project source files under this rule. This documentation change itself does not modify application files.

Release

Branch, tag, and publication steps are in gitworkflow.md.

  • Smoke-test the packaged macOS build, not only the unit suites. Record the desktop, Kubernetes, OpenShift, Helm, and authentication versions you exercised.

Artifacts to add when implementation starts

Process skills already come from the agent environment. These repo artifacts do not exist yet. Add them with the first implementation change, not during planning.

  • .cursor/rules/ponytail-lite.mdc, always on.
  • Husky on commit only, as in Hooks: lint-staged with prettier --write for HTML and TypeScript, eslint --fix, and gofmt -w. No test hook.
  • A pull request template whose validation box is the Go and frontend commands, plus a post-review section that lists findings as KSF-001 style ids.
  • .agents/skills/ for kubesift-code-review, kubesift-code-hygiene, and release. Keep one canonical SKILL.md per skill; add tool-specific links only if needed.
  • Strict schemas for application-owned settings/helper trust and later provider profiles; Kubernetes-compatible kubeconfig parsing with explicit helper validation.
  • Conventional Commits, so the release skill can build a changelog without a human rewrite.

Process skills set the order of work. Repo skills know this codebase. Ponytail decides how much code is enough. Invoke the process skill before editing. If two apply, the process skill goes first.

For Kubernetes readers, relationships, status presentation and integration tests, use the KubeSift Kubernetes development skill and Kubernetes reference index to find official API documentation and project decisions.

Sub-agents

Dispatch a fresh sub-agent when the task needs a clean context: review, a wide search, or one plan task. Give it the repo path, the diff or the task, and the spec. Do not hand it the coding session’s history.

Phase 2 provider and agent design may use ai-architect. Desktop packaging and performance stay in this playbook and the roadmap. Web-host deploy and web-vitals agents are for a different kind of application.

Rules that keep sub-agents useful:

  • One reviewer per review. Two reviewers of the same diff in parallel produce two lists and no owner.
  • Review sub-agents do not modify code.
  • An implementer sub-agent gets one task, the files, and the test command. The parent integrates.
  • Parallelize only when tasks share no files and no state.
  • If a fresh reviewer is unavailable, report the independent review gate as blocked. Self-review does not satisfy it.

Decisions another playbook must not overwrite

These belong to KubeSift. Copy the loop, not another application’s deploy path, host tools, or release artifact.

  • Wails, Go, and React/TypeScript. Wails v3 is the proposed baseline; pin a supported version at validation. Domain services do not import the desktop bridge.
  • macOS first. The shipped check is a packaged desktop build, including Finder launch. Signing, notarization, minimum macOS, and the updater are still open.
  • Connection id plus generation on every operation. Tabs own namespace filters. No global active context, and no rewrite of kubeconfig current-context.
  • Watches, logs, exec, and port forwards are sessions with explicit ids, cancellation, bounded buffers, and visible truncation. Port-forward payload traffic stays outside React. Loopback is the default.
  • Prepare, review, execute. Dry-run where the API supports it. Helm and Operator previews must say when they can touch resources outside the selected namespace.
  • Container exec is an interactive session that can write. Label the target. Do not describe it as read-only.
  • OpenShift Projects, Routes, Builds, and Operators are dedicated workflows. Generic custom resources stay on the dynamic client. Detect the APIs that are present.
  • Metrics come from an existing Metrics API and, when the user selects one, an existing Prometheus-compatible endpoint. Never forward cluster tokens to an arbitrary discovered URL.
  • AI starts in Phase 2: Claude first, then other adapters behind one contract. Profiles support an application default and per-cluster overrides, with no silent cross-provider fallback.
  • Disposable local clusters for mutation tests. The local-cluster tool is still an open choice. External integration environments require a named target and named actions. Do not discover permission by trying a write.
  • Do not claim Lens or K9s parity without a reviewed capability inventory and evidence.
  • Apache-2.0 licensing; repository workflow lives in gitworkflow.md.
