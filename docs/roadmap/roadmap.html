Delivery roadmap

Phase sequence lives here; execution tasks live in Superpowers plans.

Each increment ends in reviewable evidence and a usable outcome. Security and testing are continuous, not deferred to release. Dependencies below are the default order; changes require updating this roadmap.

  1. 1A

    Validation

    Minimal Wails integration, packaged launch, auth, two cluster sessions, concurrent streams, terminal, forwarding and controlled local write

    Exit Approved spec and execution request. Pass validation gate or revise architecture before expansion.

  2. 1B

    Explorer

    Desktop navigation/settings, contexts, cluster tabs, discovery, core/generic resource views, YAML/events/logs and filtering

    Exit 1A. Failing-Pod inspection and partial-RBAC/disconnect journeys pass.

  3. 1C

    Operations

    YAML changes, restart/scale/delete, exec/port forwards, rollout history and supported rollback

    Exit 1B. Target isolation, conflicts, confirmations and session cleanup verified.

  4. 1D

    Administration

    Helm lifecycle, current/historical metrics, cordon/uncordon/drain

    Exit 1C. Hook/cluster-scope review, PDB behavior, absent metrics and query limits verified.

  5. 1E

    OpenShift

    Dedicated Projects, Routes, Builds and Operators workflows

    Exit 1B foundation and 1C safeguards; after 1D by default. Test actual supported OpenShift APIs and permissions.

  6. 1F

    Release readiness

    Capability inventory closure, supported-environment tests, performance, accessibility, packaging, signing and release review

    Exit 1A–1E. Agreed Phase 1 scope met or explicitly deferred; no unsupported parity claim.

  7. 2A

    AI foundation

    Provider profiles, secure keys, default/overrides, Claude adapter, read-only tool contracts, sharing/redaction

    Exit Phase 1 service foundation. Validate provider routing and no credential/Secret leakage with synthetic evidence.

  8. 2B

    Investigation

    Evidence collection, metrics correlation, cited diagnoses, missing-evidence handling and evaluation scenarios

    Exit 2A. Failing-Pod AI journey passes with verifiable citations and no write access.

  9. 2C

    Provider breadth

    OpenAI/OpenRouter and additional supported adapters, model capability handling and release hardening

    Exit 2A contracts and 2B evaluation. Provider-specific compatibility proven.

2A–2C are proposed subdivisions of the accepted AI phase. OpenShift connectivity and generic resources start in 1A/1B; 1E supplies specialized workflows. No durations are promised before validation.

Release gates

  • Record tested desktop, Kubernetes, OpenShift, Helm and authentication versions.
  • Set measurable performance budgets after 1A and assess them in 1F.
  • Use local disposable clusters for mutation tests; obtain explicit targets for integration checks.
  • Verify license notices, signing and updates before releasing.
  • Keep AI remediation separate and uncommitted beyond Phase 2 investigation.
