How to plan the next phase

  1. Read this roadmap, the previous phase’s validation report, the capability inventory and the owning architecture, UX, security and engineering documents. Check the working tree and current implementation before assuming a capability exists.
  2. Carry forward unresolved acceptance items explicitly. Record whether each blocks the next phase or is a named compatibility gap. A local kind pass does not prove EKS, AKS or OpenShift authentication.
  3. Use Superpowers to write or refine a dated Markdown specification under docs/superpowers/specs/. Use the phase scope and planning questions below. Link requirements instead of copying their complete text. Review the specification with the user.
  4. After specification approval, create a Markdown implementation plan under docs/superpowers/plans/: small tasks, dependencies, affected paths, acceptance checks and a minimal meaningful verification set. Resolve current library/toolchain choices against the actual repository.
  5. Implementation happens only when requested, in its own session if desired. Follow the engineering playbook, source descriptions and Git workflow. Use the existing local development targets.
  6. Finish with a durable phase validation report: what works, actual checks, unrun environments, limitations and next-phase prerequisites. Update the capability inventory and this status summary. Do not mark a phase complete merely because code or a plan exists.

1A · Architecture and integration validation

Outcome: establish whether Wails + Go + React/TypeScript can support a packaged, concurrent Kubernetes desktop client before extending the product.

  • Validate packaged startup and desktop bridge, kubeconfig source handling, explicit connection identity and remembered/revocable credential-helper trust.
  • Exercise two independent cluster sessions, bounded concurrent logs/watches, terminal input/resize, port forwarding, cancellation and cleanup.
  • Use a narrowly scoped synthetic ConfigMap operation to validate frozen targets, review, stale identity/version rejection and RBAC handling.
  • Measure realistic load, responsiveness and cleanup. Keep packaged checks distinct from automated service checks.

Remaining planning input: read the latest acceptance matrix and final review to determine whether packaged acceptance, calibrated sustained load and repeated cleanup checks meet the gate. Carry forward recorded follow-ups; do not silently relax the gate. Derive performance budgets from valid measurements.

Exit: reviewed local architecture acceptance, documented provider/platform gaps, and a clear decision to retain or revise the architecture.

Artifacts: approved specification, execution plan, actual report. The validation UI is not the finished product UI.

1B · UI foundation and desktop experience

Outcome: implement and review the approved workspace before connecting the full explorer. Start from the single approved mock set and interaction requirements.

  • Define design tokens and reusable controls for typography, spacing, colors, focus, status, tables, tabs, forms, menus, drawers and review dialogs. Use the same hierarchy in light and dark themes.
  • Build independent cluster tabs, persistent cluster/namespace identity, user-assigned environment labels, grouped resource navigation, resource list/detail layout and the bottom Sessions dock.
  • Build Settings with System (default), Light and Dark appearance; validate system changes and saved window/pane restoration across laptop and external displays.
  • Implement selection, filtering presentation, command palette, focus handling and selected-resource shortcuts. Distinguish loading, empty, forbidden, disconnected, stale, unsupported and missing-dependency states.
  • Design the global right-side AI panel now, including context identity and payload/evidence surfaces, but keep provider integration and live investigation in Phase 2.
  • Use clearly labeled synthetic UI previews for flows without live services. Reuse stable 1A interfaces where appropriate; do not create a second Kubernetes client or imply demo actions modify a cluster.

Boundary: this is a reusable product UI milestone, not a new static mock export. Full resource discovery, production browsing and operational integrations belong to 1C–1F. Future pages need coherent navigation and state patterns, not fully functional placeholder features.

Plan decisions: approve fixture/demo boundaries, component organization, exact keyboard bindings, minimum supported window size, pane minimums and narrow-window behavior. Validate component-library choices against the existing frontend. Do not select dependencies solely to match a screenshot.

Exit: demonstrate the shell on laptop and wide-monitor sizes in both themes; independent tab state survives switching; selected-resource actions keep their target; keyboard focus works; Settings owns appearance; Sessions and the AI preview retain state across resizing. User reviews the UI before 1C expands it.

Artifacts: approved UI specification and detailed implementation plan; then a UI validation report with screenshots, tested sizes and remaining issues. Keep tests minimal: representative state/target checks plus a focused visual/manual checklist.

1C · Live multi-cluster explorer

Outcome: select a context and namespace, inspect a failing Pod and see its actual status, events, configuration and relevant logs in one workspace.

  • Discover local kubeconfigs and explicitly selected sources; list contexts without rewriting the global current context. Reuse oc login, AWS CLI/SSO and Azure CLI credential flows under the helper trust policy.
  • Connect multiple clusters in separate tabs with independent namespace, selection and connection state. Explain missing helpers, expired login, untrusted helper changes and inaccessible API servers.
  • Discover core and custom APIs. Provide dedicated useful views for workloads, networking, configuration, storage, nodes and access-control resources, with generic list/detail/YAML access for other discoverable kinds.
  • Cover Pods, Deployments, StatefulSets, DaemonSets, Jobs/CronJobs, Services, Ingresses, ConfigMaps, Secrets, PVCs/PVs, namespaces, nodes and RBAC resources according to supported API versions and permissions. Follow security policy for Secret reveal; do not treat unrestricted YAML as a bypass.
  • Connect Overview, Events, YAML and Logs; container selection, previous logs, follow/stop, timestamps and filtering. Handle watches, refresh, pagination/large lists and stale/disconnected data without unbounded retention.
  • Generic OpenShift/custom-resource access starts here; dedicated workflows arrive in 1F.

Plan decisions: define initial kind coverage and generic fallbacks, all-namespace behavior, discovery caching, list/watch boundaries, large-list budgets and log limits. Resolve local-machine shell versus Pod exec in the capability inventory; Pod exec is committed in 1D, local-machine shell is not silently implied.

Exit: failing-Pod inspection passes against local fixtures; partial RBAC does not break the whole explorer; two clusters with matching resource names remain isolated; inaccessible APIs and disconnected streams recover predictably. Record real EKS/AKS/OpenShift auth smoke results separately.

Artifacts: approved explorer spec and task plan, resource coverage table, validation report and service contracts reusable by operations and AI.

1D · Resource operations and interactive sessions

Outcome: act on the resource being inspected with explicit target review and understandable failure handling.

  • Edit/apply YAML with diff and conflict handling; restart, scale and delete supported resources; expose rollout history and rollback for supported workload kinds.
  • Provide Pod/container exec terminals and port forwarding with explicit endpoint/container selection, local port conflict handling, terminal resize and visible stop controls in Sessions.
  • Use RBAC-aware availability and server authorization. Bind prepared actions to connection generation, namespace, kind/name and resource identity; switching tabs must not retarget review.
  • Confirm destructive/disruptive actions, invalidate stale reviews and explain partial/failed results. Never blindly retry an ambiguous write.

Plan decisions: supported apply/patch semantics, rollback kinds, delete propagation/grace settings, terminal command selection and session restore policy. Decide bulk actions explicitly; they are not implied by single-resource actions.

Exit: representative local edits/restarts/scales/deletes and rollback work; stale UID/version and permission denial fail safely; streams and forwards stop cleanly; session ownership survives navigation and is resolved on tab/app close.

Artifacts: operation matrix with permissions and review requirements, approved spec/plan, targeted safety checks and local validation report.

1E · Helm, metrics and node administration

Outcome: administer existing clusters without installing supporting infrastructure for KubeSift.

  • Helm: list release status/history, inspect values/manifests, and user-initiated install, upgrade, rollback and uninstall. Review hooks, cluster-scoped resources, namespace impact and sensitive values before execution.
  • Metrics: read current Pod/node CPU and memory from available Metrics API endpoints. Label missing data as unavailable, not zero; label percentage denominators such as requests, limits or node capacity.
  • Historical metrics: discover or explicitly configure existing Prometheus-compatible sources, including supported OpenShift monitoring. Use authorized bounded queries and managed local access; show source, time range, freshness and missing-series states.
  • Node operations: cordon, uncordon and drain with disruption review, eviction/PDB behavior, DaemonSet/local-data considerations, progress and cancellation. Do not default to force or PDB bypass.

Plan decisions: Helm SDK integration and supported versions, chart source/auth handling, metrics endpoint selection and transport, query budgets, drain timeouts and override policy. KubeSift never installs a metrics stack, agent or CRD for its own operation; explicit user Helm/Operator installs are a different workflow.

Exit: Helm lifecycle works on dedicated fixtures; missing metrics sources degrade gracefully; historical data identifies its source; drain respects blocking PDBs and explains remaining work. Do not disrupt shared review clusters to prove drain.

Artifacts: approved administration spec/plan, compatibility/query contracts and focused validation report. Any disruptive test environment needs an explicit plan consistent with local-development ownership.

1F · Dedicated OpenShift experience

Outcome: OpenShift users get purpose-built workflows alongside generic custom-resource access.

  • Projects: project selection, metadata/status, visibility and authorized lifecycle operations with scope review.
  • Routes: backend/service relationships, host, TLS mode, admitted conditions and authorized configuration changes without exposing private key material by default.
  • Builds: BuildConfig/Build relationships, status, logs and supported start/cancel/rebuild workflows, with clear source and target.
  • Operators: discover available APIs, show catalogs, subscriptions, install plans, installed versions and health; support explicit installation, upgrade approval and removal with dependency/cluster-scope review.

Plan decisions: exact OpenShift versions and Operator APIs, supported verbs per workflow, absent API behavior, permission boundaries and test environment. Do not assume all OpenShift installations expose the same Operator lifecycle API.

Exit: dedicated journeys validated against an explicitly authorized supported OpenShift environment; ordinary Kubernetes clusters omit unavailable integrations cleanly. Synthetic CRs on kind can test rendering but cannot prove OpenShift compatibility.

Artifacts: reviewed workflow/API coverage, approved spec/plan and actual compatibility report with unrun cases.

1G · Phase 1 release readiness

Outcome: a usable macOS distribution with an honest support matrix and operational safeguards already exercised.

  • Reconcile every required capability with implementation/evidence. Review unresolved bulk actions, local shell, file copy and extensions; explicitly include or defer them. Do not claim Lens/K9s parity from broad discovery alone.
  • Validate supported Kubernetes/OpenShift versions, EKS/AKS/oc credential renewal, missing helper behavior, reconnect, sleep/wake, multi-monitor layout, accessibility and large-resource/stream performance.
  • Decide minimum macOS version and architectures, packaging/signing/notarization, updater behavior and release process. Windows/Linux remain later unless separately approved.
  • Review credential storage, logs, diagnostics, dependency/license notices and Apache-2.0 distribution requirements using the existing security and engineering owners.

Exit: explicit release scope, passing applicable gates, disclosed limitations and actual tested artifacts. A release requires separate authorization.

Artifacts: capability closure, compatibility/performance/accessibility results, release checklist and user-facing installation/troubleshooting documentation.

2A · AI providers, sharing and read-only tools

Outcome: securely connect the global AI panel to a configured provider and reusable Kubernetes query services.

  • Application-wide default provider with per-cluster overrides; secure API-key storage, model configuration and clear effective routing. Claude first; design adapters for later providers without embedding Claude assumptions in domain services.
  • Enable Ask AI on every page as a right-side resizable panel. Show explicit target/no-target states; existing investigations do not silently follow navigation.
  • Define read-only tools, RBAC behavior, bounded collection and cancellation. Treat cluster content as untrusted input, not executable model instructions.
  • Apply data-sharing controls and redaction; exclude credentials and Secret values. Preview redacted payload before submission and show the actual sanitized payload afterward. Do not promise perfect sensitive-data detection.

Plan decisions: profile binding, unsupported model/tool behavior, token/data budgets, retention, retry/rate-limit behavior and override changes during an investigation. Never silently fall back to another provider or key.

Exit: synthetic tests prove correct profile routing, denied tools and protected data handling; cancellation and provider errors preserve workspace state. No AI mutation tools.

Artifacts: approved AI foundation spec/plan, tool/provider contracts and security evaluation report linked to the owning security model.

2B · Evidence-backed investigation

Outcome: select a failing Pod, ask for investigation and receive a likely diagnosis grounded in its actual cluster evidence.

  • Correlate Pod state, events, relevant workload configuration, bounded logs and available metrics; retain evidence identity and collection time.
  • Show observations, hypotheses, unknowns and next checks with citations that open the captured evidence. Preserve the investigation’s target while the user browses elsewhere.
  • Handle missing/forbidden/stale evidence, provider failures and conflicting sources honestly. Historical metrics are conditional on an existing accessible source; Prometheus metrics are not logs.
  • Evaluate representative missing configuration, image pull, crash, resource pressure and scheduling scenarios using synthetic fixtures.

Plan decisions: capture freshness, evidence retention, context refresh/review, citation navigation and criteria for useful versus unsupported diagnoses. AI recommendations do not authorize operations.

Exit: the failing-Pod journey produces traceable evidence and useful uncertainty; fabricated citations and unsupported certainty are caught by evaluation. Missing observability does not block basic status/events/log investigation.

Artifacts: investigation spec/plan, small scenario corpus and reviewed diagnosis/evidence report.

2C · Provider breadth and AI release readiness

Outcome: users can choose verified providers with their own API keys while retaining the same safeguards and investigation experience.

  • Add OpenAI and OpenRouter adapters; evaluate further APIs against explicit compatibility contracts. An arbitrary API key alone does not guarantee a provider/model supports the necessary operations.
  • Validate streaming, tool calls, cancellation, errors, context limits and model capability negotiation per adapter. Make unsupported models understandable.
  • Repeat routing/redaction and diagnosis checks across supported providers; document endpoint, model and key setup. Distinguish API access from subscription or CLI credentials.

Exit: tested provider/model support matrix and reviewed AI release evidence; per-cluster overrides remain reliable with no implicit cross-provider fallback.

Artifacts: adapter specs/plans as needed, provider compatibility report and updated user guide. AI remediation remains a separate future design, not an implicit Phase 2 deliverable.
