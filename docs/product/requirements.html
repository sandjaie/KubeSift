KubeSift / Planning

Product requirements

A complete operations client first. Evidence-backed AI second.

Purpose and users

KubeSift is a local-first Kubernetes desktop workspace for DevOps and SRE engineers. It brings resource inspection, logs, events, configuration and operational actions into one workspace. Broad Lens/K9s-inspired capability is the ambition; exact feature parity must be verified against an inventory, not assumed.

Agreed scope

  • Phase 1: full operations client delivered incrementally, with independent cluster tabs and clearly visible cluster/namespace identity.
  • Phase 2: AI investigation based on actual cluster evidence; AI is a core product capability.
  • macOS first; Windows/Linux later. OpenShift, EKS and AKS are compatibility targets.
  • Reuse local kubeconfigs and existing oc login, AWS CLI SSO and Azure CLI authentication workflows.
  • No in-cluster component installed for KubeSift’s own functionality. User-initiated Helm and Operator installations are supported.
  • Open-source project licensed under Apache-2.0.

Phase 1 capabilities

Area Required behavior
Connections Discover default kubeconfig and KUBECONFIG sources; add files; select contexts; explain authentication, network and RBAC failures.
Resources Workloads, networking, storage, configuration, nodes, namespaces, RBAC, quotas, limits, autoscaling, events, CRDs and discoverable custom resources.
Inspection Tables, filtering/search, status, relationships, YAML, events, current/previous container logs and interactive container terminals.
Operations Edit/apply YAML, restart, scale, delete, port forward, supported workload rollback and node cordon/uncordon/drain.
Helm Inspect releases, values, manifests and history; install, upgrade, rollback and uninstall with target review and applicable confirmations.
Metrics Current CPU/memory from existing Metrics API; historical charts from an existing accessible Prometheus-compatible source. No automatic installation.
OpenShift Dedicated Routes, Projects, Builds/BuildConfigs and Operators workflows, with generic access to other custom resources.

Generic access covers server-exposed resources and supported verbs permitted by RBAC. It does not promise specialized forms for every CRD or bypass inaccessible APIs. A container terminal means exec inside a selected container; a local host shell is not yet committed scope.

OpenShift workflows

  • Routes: inspect host, backend Service, TLS and admission; create/edit/delete and navigate to related resources.
  • Projects: browse/switch, inspect quotas and access, create/delete where permitted using the appropriate OpenShift APIs.
  • Builds: inspect Builds/BuildConfigs, start/cancel builds, stream logs and inspect output references.
  • Operators: inspect subscriptions, installation plans, versions, managed resources and upgrade status; install and manage supported lifecycle operations with impact review. Detect the Operator APIs present; avoid assuming every cluster uses the same lifecycle mechanism.

Acceptance journeys

  1. Failing Pod: choose cluster and namespace → select Pod → inspect status/events/YAML → view selected container logs → exec if permitted. Disconnection and permission failures remain understandable.
  2. Safe multi-cluster action: prepare a change in cluster A, switch to B, confirm the original operation. It must remain bound to A; stale targets must require re-evaluation.
  3. OpenShift: select Project → inspect Route and Service → follow Build → inspect Operator state. Absent APIs or denied permissions do not break unrelated views.
  4. AI: select failing Pod → identify effective provider/sharing policy → collect permitted evidence → return observations, likely causes, citations, uncertainty and next checks. No credentials or Secret values are sent.

Approved workspace behavior, themes, global AI entry point and responsive layout are owned by the UX specification.

Quality expectations

Keyboard navigation, visible focus, readable information density, explicit stale/forbidden/offline states and labels that do not rely on color alone. Performance budgets will be set from validation measurements; no unmeasured latency or memory claim is accepted.

Scope still requiring refinement

Exact Kubernetes/OpenShift version matrix, minimum macOS and architecture support, Helm compatibility, bulk operations, local host terminal, file transfer, extension system and advanced observability integrations remain open. See the capability inventory and decision register. Phase 1 is not complete merely because the first Pod journey works.
