Packaged load and cleanup

The actual renderer ran two Pod watches, four log follows, one xterm terminal and one loopback forward across the two approved local clusters. Its measured load span was 600.001 seconds; the disposable B flood lasted 64.876 seconds. Fixed 55-second windows of CRI timestamps measured A and B baseline at 100.0 lines/sec each and the B flood at 2000.364 lines/sec, all with 256-byte lines and within the declared ±2% tolerance. Twenty terminal probes passed through xterm's parse callback: median 50 ms, nearest-rank p95 52 ms. Ten starts of the final UI package reached frontend Ping: median 696.6 ms, nearest-rank p95 3888.1 ms, retaining the cold first sample.

All twenty explicit start/stop cycles completed. After cycle 20, native sessions, queued bytes and in-flight bytes were zero; native goroutines were 15 versus 14 before load, and cycle samples ranged 13–15. All twenty stopped forward ports were unreachable. Native RSS first/last/max was 122,814,464 / 52,314,112 / 127,385,600 bytes; WebKit XPC memory is excluded. Four active log histories remained capped at 1 MiB each. The corrected cumulative observed-session-error counter stayed at zero.

Observed degradation: native log drops totaled 67,920,384 bytes. While WebKit was backgrounded or occluded, renderer receipt stayed at 52,527,616 bytes from roughly 192–599 seconds and native queues rose to about 4.2 MiB. Bringing only the package window forward around 600 seconds resumed acknowledgements; the queue drained by about 605 seconds. Truncation and native drops were visible and bounded. The run does not establish uninterrupted foreground throughput or lossless logs. Proposed one-host budgets are labeled as proposals in the numeric summary, not retrospective pass thresholds.
