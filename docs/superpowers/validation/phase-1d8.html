Phase 1D.8 server-side apply validation

Started 17 November 2026 Dubai time from develop at 4b59c44. See the specification, plan, and Phase 1D closure audit.

Existing-resource safety gate

TestExistingApplyProtocol sent the same guarded apply media type and strict options planned for the app to kind-dev-local-a and kind-dev-local-b, both Kubernetes v1.37.0. On each server, a ConfigMap and a synthetic Widget had the following results:

Case HTTP status Object readback
Matching UID/version, dry-run 200 Live object stayed unchanged.
Matching UID/version, real write 200 Value updated; UID was preserved.
Stale version, with and without force 409 Current version and value were unchanged.
Same name with a different UID and current version, with and without force 422 Replacement stayed unchanged.
Deleted after GET, with and without force 409 Object stayed absent.

There was no HTTP 201 in the representative real-server cases. A synthetic 201 response verifies that the app records Unknown with an unsupported-safety diagnostic and performs no cleanup mutation or replay.

Automated and live integration evidence

scripts/check.sh passed source descriptions, documentation links, Go tests and vet, binding normalization tests, 113 frontend tests, lint and typecheck. Race checks covered operations, the desktop bridge, Kubernetes reads and sessions. Normalized binding regeneration, production bundling, wails3 task package and strict signature verification passed.

TestYAMLApply verified both contexts with ConfigMaps, Secrets, a namespaced Widget and a cluster-scoped PriorityClass. Real managedFields showed shared ownership after a same-value apply, a conflict with the original manager, exclusive ownership after deliberate takeover, and release/removal of an omitted owned value. Another manager’s field survived. The tests also checked Secret stringData precedence, exact custom numeric data, list replacement as determined by the API, and forbidden Patch with Get allowed.

Native synthetic checks cover same-address locks across actions and API versions, exact guarded bytes, abort/staleness before dispatch, post-GET races, unexpected or lost responses, response differences, and recovery of an existing result without a second PATCH. Retained results omit manifests and response values. Mounted checks cover explicit takeover, same-value confirmation, delayed completion, preservation of the exact draft after Unknown and rejection of late results for a different draft.

The Create, Edit, retained-history Rollback and interactive integration suites passed on both contexts. A separate legacy Restart probe stopped before any mutation because its owned restart fixtures were absent. Its original acceptance remains in the 1D.2 report.

Packaged macOS verification

The walkthrough ran on arm64 macOS 26.7.1. The signed package was rebuilt after adding transient apply response evidence; a new ConfigMap apply and accepted-result refresh passed on context A.

  • A ConfigMap opened from an identity-only editor with initial Cancel focus. The dry-run showed the actual owner and field, with no Confirm until deliberate takeover. Confirmation returned Accepted, and Open target showed the new value and the preserved field.
  • A Secret began in metadata-only browsing. Apply opened directly without a second reveal. A synthetic stringData value was accepted and verified against the server. Edit still opened the captured YAML; Create still opened a separate editor.
  • On B, a same-value apply showed that ownership could change and kept Confirm available. A later stale submission showed Target changed, and resuming the draft restored the exact text. A read-only B credential saw Forbidden with no takeover or Confirm.
  • Using one Get/Create/Patch credential without List permission, created a Badge via v1beta1, opened it from the create result, applied with deliberate takeover, then opened and refreshed the apply result at v1beta1 with the original UID. The resource sidebar preserved its collapsed group across A/B. Light and Dark were checked, Escape dismissed the editor, and the original appearance and sidebar state were restored.

Server readback verified both desktop ConfigMaps, the Secret and the custom object. The custom object was removed before its CRD, and UID-protected fixture namespaces, RBAC objects and isolated kubeconfigs were removed.

Limits

Real-server validation covers the two local kind servers, with packaged checks on arm64 macOS. Admission response differences and unexpected success statuses were synthetic; no admission webhook was added for verification. The ownership summary can be incomplete for cross-version managed fields or exceed its display cap. Kubernetes acceptance does not establish controller convergence.
