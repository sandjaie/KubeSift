Phase 1E.2 Helm management validation

Agent verification on 18 November 2026, Dubai time. Implemented from develop 0ba4d2d (containing 10ed221) on feature/phase-1e2-helm-management. See the approved specification and six-task plan. Independent review and publication are pending; no release was requested.

Environment and supported coverage

macOS 26.7.1 on arm64, Go 1.27.3, Node 25.9.0, Helm SDK 4.3.1, Kubernetes API/client-go 0.37.1 and kind Kubernetes 1.37.0. Helm 3.19.0 (3d8990f) was used only to seed compatibility records. The shipped app uses the SDK, not a Helm executable.

Native management covers install, replacement-values upgrade, retained-revision rollback and uninstall with Secret or ConfigMap release storage. Sources are native-selected packaged charts, HTTPS index repositories and exact OCI tags/digests. Credentials remain in native session memory; TLS CA and client certificate/key references are nonsecret persisted metadata. No ambient registry credentials, credential helpers, plugins, post-renderers or dependency downloads are used.

Packaged desktop observations

Agent-operated native macOS checks used the packaged Wails application, not a browser substitute. The existing Helm list/detail layout, Settings surfaces, dialogs and themes were preserved.

  • Saved a private HTTPS source with a CA selected through the native picker; metadata survived restart. Supplied synthetic session credentials and resolved version 1.1.0 through the authenticated repository.
  • Installed local version 1.0.0 with explicit namespace creation, upgraded to 1.1.0 with edited replacement values and a custom resource, rolled back revision 2 to revision 1 (creating revision 3), and uninstalled while explicitly retaining history. Native results showed deployed/uninstalled revisions and exact context/namespace/release/storage labels.
  • Reviewed values and manifest differences, hooks, CRDs, retention warnings and namespace impact. Cancel received initial focus; keyboard input and selection worked. Confirmation stayed unavailable while preparation was incomplete.
  • Opened a current ConfigMap from retained Helm resource evidence and used Back to release. Settings navigation preserved an active waiting hook; cancellation showed “Outcome unknown” and a refresh-before-recovery warning.
  • Dark upgrade and light uninstall/result views were observed. No Helm process was present during native operations, and the synthetic password was absent from app files and its captured log.

The failing-hook install showed an explicit failed result and observed failed revision; cancellation retained its distinct uncertain result. The temporary source was forgotten and removed, the app exited, and the loopback server stopped. The desktop namespace and labelled CRD were deleted and both approved clusters were checked for fixture absence. Independent review is pending. These agent observations are not a claim of personal user UAT; no duplicate user checklist is required.

Curated native screenshots show the dark upgrade review, light uninstall review, and failure/cancellation outcomes.

Corrections found by verification

The first live run exposed a namespace fallback in the SDK's raw-config loader: release storage was correctly scoped but resource creation fell back to default. An explicit namespace override fixes the common loader; a focused regression failed before and passed after the fix. The exact synthetic misplaced ConfigMaps were ownership-checked and removed from both clusters. Live reruns verified resources in the requested namespaces. A second live failure exposed the SDK's required wait strategy during uninstall dry-run; preview now supplies the owned wait context and strategy. The final suite and package include both corrections.

Fixture-only corrections refreshed the superseded revision's resource version before rollback and started Docker before the live run. Neither failed attempt is counted as passing evidence.

Limits and unrun environments

The local authenticated OCI fixture does not establish compatibility with every cloud registry or OAuth provider. No cloud cluster, Windows/Linux package, notarization or release publication was tested. Charts must include dependencies and self-contained standard JSON Schema; values reject aliases and excessive nesting. Content hashes identify pinned bytes, not publishers. Helm preview cannot promise later admission, hook, lookup or time/random outcomes; partial effects can remain after failures and cancellation. Rendered-output limits are enforced after the SDK returns its rendered content, not as a hard memory sandbox around arbitrary template execution.
