Phase 1D.5 workload rollback validation

Verified on 16 November 2026 from develop 2f74b4c. See the approved specification and implementation plan.

Automated verification

scripts/check.sh passed source descriptions, documentation links, formatting, Go tests and vet, and 103 frontend tests plus lint and typechecking. go test -race ./internal/operation, Wails bindings, npm run build, wails3 task package and strict macOS signature verification passed.

Native tests checked exact owner and source identity, large and duplicate revisions, forbidden and partial history, malformed ControllerRevision data, and Deployment hash removal. Execution tests exercised server preview changes, denied dry-run, a changed source, a late parent conflict, duplicate Confirm, the shared edit lock and an ambiguous response without a second write. The frontend test covered revoking a late preview and requiring the same captured parent and source at confirmation.

History extraction follows Kubernetes v1.37.0 StatefulSet and DaemonSet history writers and the Deployment hash cleanup in kubectl. A DaemonSet dry-run can increment a legacy API-generated template-generation annotation; it is not a requested write path.

Approved local API servers

On kind-dev-local-a and kind-dev-local-b (Kubernetes v1.37.0), ran KUBESIFT_ROLLBACK_INTEGRATION=1 go test -tags=integration ./tests/integration -run '^TestWorkloadRollback$' -count=1 -v with an isolated A/B kubeconfig directory. All six controller/context cases passed. The workloads produced real retained history. API reads confirmed dry-run did not persist and Confirm restored the selected template while preserving every other spec field, including the paused Deployment, StatefulSet partition and claim template, and OnDelete DaemonSet. A stale parent version was rejected on both contexts.

Packaged macOS verification

  • On arm64 macOS 26.7.1, opened each controller's Revisions tab, selected an owned source, and saw the actual Pod-template diff and successful server dry-run. The reviews showed the paused Deployment, StatefulSet partition, OnDelete DaemonSet and zero desired replicas or Pods. From a DaemonSet revision, inspected the source and went Back to the original workload.
  • Confirmed the selected Deployment and StatefulSet rollback on A. Operation results described Kubernetes template acceptance separately from Pod readiness. From B, Check workload on A's result opened A's original StatefulSet Overview and generation evidence.
  • Selecting the current Deployment revision on A produced a no-change message without Confirm. Advancing the same-named Deployment on B after preview caused Confirm to be rejected. API reads showed the original A marker restored, B's current marker unchanged, and the StatefulSet partition and replica count preserved.
  • Checked the existing split view and rollback review with Dark and Light and restored Dark. Closed the app, removed the fixture namespaces by recorded UID, verified their absence on both contexts, and removed the isolated kubeconfigs.

The fixtures use zero replicas or a node selector that matches no nodes. They prove template acceptance, not Pod convergence. The native HTTP test covers denial and ambiguous responses; neither was induced in the packaged app. No other operating systems, clusters or vendor-specific history sources were exercised.
