# Phase 1E.5 · Reviewed Node administration

## Operator outcome

From the selected Node’s Actions menu an operator can prevent ordinary new scheduling (Cordon), allow it again (Uncordon), or review and request graceful removal of eligible Pods (Drain). Drain cordons first and leaves the Node cordoned, including after partial progress. Returning it to service is a separate reviewed action. The [roadmap](../../roadmap/roadmap.html#phase-1e) defines the Phase 1E exit. The [security model](../../security/security-model.html) and [reviewed operations workflow](../../ux/workflows.html) own the common safeguards. Baseline is develop at `8a6b649`, after Phase 1E.4.

Use native Kubernetes APIs and the existing operation coordinator. A kubectl subprocess would introduce a second credential and process lifecycle and would not bind its changing Pod list to the operator’s review. The first version offers no destructive overrides. Operators may cordon independently when a drain is blocked.

## Review and permissions

Bind every review to connection ID/generation, core/v1 cluster-scoped Node name, UID, captured resourceVersion, action and reviewed settings. Use a cancellable preparation, the coordinator’s five-minute single-use token, canonical Node lock shared with YAML operations, retained results and production confirmation conventions. Show cluster/environment and exact Node. Require typed Node name for drain in all environments and for production scheduling changes. An ordinary cordon/uncordon requires explicit confirmation. Review cancellation/expiry has no lasting cluster effect.

Cordon/uncordon requires named Node GET and PATCH. Read and display the current unschedulable flag. Already in the requested state returns a verified no-op. For a change use a JSON Patch with tests on UID/resourceVersion and add or replace only spec.unschedulable. Server dry-run and inspect the response, then send the same guarded patch once after confirmation. Stale review, denial, unsupported dry-run or unexpected admission changes require a fresh review. Never change taints or imply the node is Ready. A successful uncordon allows ordinary scheduling, subject to other constraints.

For drain require a complete, bounded, all-namespace Pod LIST filtered server-side by spec.nodeName, even in a namespace-filtered workspace. Show the cross-namespace scope before review. Follow consistent list pagination, 100 rows/page, maximum 500 assigned Pods, 30 s preparation deadline and existing HTTP body caps. Reject incomplete/expired lists. Use discovery for policy/v1 Eviction and scoped permission reviews for create on core pods/eviction in candidate namespaces, plus required reads and patch when applicable. A definitive denial or unresolved essential access blocks confirmation. Do not test access by attempting a real eviction. Budget names/status may be supplementary when readable. The eviction API adjudicates current admission. [API-initiated eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/api-eviction/)

## What the review counts

Project only namespace/name/UID, classification and safe reasons. Group rows by outcome and show counts even with collapsed groups. Classify in this order:

1. Mirror Pods remain. Live apps/v1 DaemonSet-owned Pods remain after verifying the controlling owner by namespace/name/UID. Explain that these Pods can still run on a cordoned Node. Unknown or dangling DaemonSet ownership blocks.
2. Already terminating Pods are observed until their reviewed UID disappears. They receive no eviction. A stuck finalizer or long grace period can leave work outstanding.
3. For other Pods, block on unmanaged, unknown, multiple, deleted or unverified controlling owners. Support live matching ReplicaSet, StatefulSet, Job and ReplicationController owners for eviction. A known controller does not guarantee a replacement becomes Ready. Terminal Pods follow the same conservative ownership/storage rules.
4. Block eligible candidates using emptyDir (including memory-backed), hostPath, a generic ephemeral volume whose claim is tied to the Pod, or inline CSI storage whose lifetime the app cannot establish. Show a plain-language reason for each. Existing PVC-backed storage can still restrict rescheduling, including local PVs; disclose that constraint without asserting portability. Never promise data in a container’s writable layer survives eviction.
5. Remaining reviewed Pods are candidates for ordinary graceful eviction. Preserve each Pod’s termination grace and identity. The only selectable disruption setting is total wait time, 2, 5 (default) or 10 minutes. No Pod DELETE, zero-grace override, forced unmanaged eviction, PDB bypass, finalizer removal or automatic uncordon.

Any blocker in the initial review prevents the entire drain, including its cordon. A complete inventory with only skipped Pods can be confirmed, with the skips visible. If already cordoned, disclose it and skip the patch. A server dry-run for the scheduling patch shows proposed scheduling state. An inventory or a dry-run never reserves disruption budget or guarantees a later eviction.

## Confirm, observe and stop

- On confirm, bind the token to one operation ID. Before the first write, re-read Node identity/state/version and repeat the complete inventory and safety classification. New candidate, newly unsafe Pod or changed impact invalidates review. Disappearance of reviewed Pods is safe to record. Pod status churn alone need not invalidate intent. Never add a new UID to the approved candidate set.
- Once cordon is acknowledged, re-read Node UID and cordoned state before each eviction and final assessment. An external uncordon, changed identity or lost access stops further dispatch. Node and Pod writes are separate server operations. This check bounds the race and cannot make them atomic.
- Immediately before each POST, re-read the named Pod and verify nodeName, UID, controlling owner, deletion state and local-data policy. Attach DeleteOptions preconditions for reviewed Pod UID and freshly verified resourceVersion to a policy/v1 Eviction on the core named pods/eviction subresource. Retain ordinary grace. Confirm on the supported API server that stale preconditions protect a replacement. If a safe conditional eviction cannot be demonstrated, leave drain disabled and report the blocker.
- Serialize evictions, observing each accepted Pod UID until it disappears before proceeding. Distinguish accepted, terminating, gone, skipped, budget-blocked, denied, changed and unknown. Limit each HTTP call to 10 s or remaining time, whichever is shorter. Poll disappearance at most every two seconds. A replacement under the same name is never evicted without fresh review. Treat explicit budget rejection as waiting for budget; distinguish generic throttling and honor Retry-After within the total deadline. Retry only definite budget or throttling 429 rejections, after revalidation, with bounded delay (default 5 s, minimum 1 s). Report long Retry-After that exceeds remaining time. Never replay a successful or ambiguous write. A lost response stops dispatch and permits read-only reconciliation.
- One active drain per connection, at most two app-wide. Run confirmed work independently of the initiating view. A native operation ID addresses progress/cancel and survives tab navigation. Keep bounded snapshots with per-Pod states; poll only visible results at most once per second. Cancel is idempotent, stops future dispatch and interrupts native waits/requests. Disconnect, deadline or app shutdown cancels local work. In-flight requests may already have taken effect. Closing review differs from closing a running progress view. Reuse existing close/quit warnings where applicable.
- Final read checks current Node identity/cordon and a fresh complete assigned-Pod list. Success means the Node is observed cordoned and only documented skips remain at that time. New Pods, timeout, denied observations or lingering Pods preclude success. Report observed progress, unresolved names and scheduling state (or unknown), including when cancellation occurs before the first write. Do not promise that replacement workloads are healthy or that future Pods cannot bind directly. Resuming unfinished work starts a fresh review. [Safe drain semantics](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/)

## UI and acceptance

Extend the existing resource Actions pattern in Node detail. Offer the scheduling action matching the captured state, plus Drain. Reuse the review/result surfaces, accessible controls, themes and narrow layout. Describe emptyDir as temporary Pod storage and PDB as a rule that protects application availability. Keep current/history metrics and other resource controls usable. Results must surface partial work after switching tabs and distinguish “cordoned” from “drained.”

Prove single dispatch, conflict/replacement guards, unsafe inventory blocking before writes, PDB enforcement, cancellation and final observation. Use real API-server fixtures on the approved kind contexts and native packaged desktop checks. The project creates single-control-plane development clusters. Use task-owned synthetic Node API objects, isolated workloads and restricted credentials. Never perform node actions on the actual kind host or evict pre-existing workloads. Record exactly which results use a real API, scripted faults or a real kubelet. Verify Phase 1E exit evidence across its five increments before claiming closure.
