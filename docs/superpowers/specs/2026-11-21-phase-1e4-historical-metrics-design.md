# Phase 1E.4 historical metrics

## Outcome

An operator investigating a selected Pod or Node can open **Historical usage** below Current usage, choose a source and time range, and see CPU and working-set memory evidence for that target. History remains usable when Metrics Server is absent. Current metrics, inventory, permissions and resource actions continue independently when history fails. Planning baseline is develop at `8a7f927`. The [roadmap](../../roadmap/roadmap.html#phase-1e), [architecture](../../architecture/overview.html) and [security model](../../security/security-model.html) own the broader requirements.

## Source and trust boundary

Use explicit HTTPS configuration for existing Prometheus-compatible APIs. Offer a user-triggered OpenShift suggestion via a named GET of route.openshift.io/v1 Route openshift-monitoring/thanos-querier on the owned connection. Suggest only an admitted TLS host, require selection/confirmation of the exact destination, and keep manual entry available if discovery is denied. No automatic endpoint probes or Service/Route listing. A second transport such as automatic port forwarding adds listener, identity and TLS lifecycles; the first increment supports endpoints already reachable over trusted HTTPS. No product provisioning or collection.

One active source per connection generation, in memory. In the Historical usage disclosure show the connection and source host, resource scope, replacement/removal and an optional masked provider bearer input. Before first use the operator confirms the endpoint serves this cluster alone or enters the exact nonempty provider-side value of the fixed label `cluster` on a shared source. Apply that matcher to every selector for shared sources. The single-cluster assertion is an operator trust decision. Missing labels on a shared endpoint yield no matches. Never infer a cluster label from a context name.

Accept an HTTPS origin only (host and optional port). Reject userinfo, paths except root, query, fragment and non-HTTPS schemes. Native code owns the HTTP client with ordinary OS certificate/hostname verification, no redirect following, cookies, kubeconfig auth, proxy credentials or inherited client identity. For a private CA, allow an explicitly selected, bounded PEM CA certificate file using the existing Helm CA validation pattern. Load roots for this origin and generation only, retain hostname verification and never modify the machine trust store. Reject invalid PEM and explain trust failures. Use a provider-specific bearer supplied for that exact origin or the endpoint's anonymous access. Only a user action may submit a new source or credential. Clear the input after submission. Never echo the secret in read models, URLs, logs, preferences, errors or evidence. Require the expected native revision on configuration changes, including after removal. Keep a revision for the empty state to reject stale submissions. Changing origin, TLS trust, credential, mode or cluster binding cancels reads, clears results and rotates the native source ID. Disconnect/quit clears source state. A selected source expresses intent; the provider independently enforces its own access policy. The app never grants roles or broadens access after denial.

Support an externally reachable OpenShift Thanos Querier HTTPS route for an identity authorized by that provider. Also support an explicitly reachable HTTPS project-tenancy endpoint as a distinct source mode: send the exact selected Pod namespace as the provider's namespace argument on each request. Disable Node history in project mode. Switching modes requires explicit source replacement. A cluster-wide route plus a namespace matcher does not supply tenant isolation. Record the supported endpoint contract and actual test environment separately. [Red Hat monitoring API access](https://docs.redhat.com/en/documentation/monitoring_stack_for_red_hat_openshift/4.21/html/accessing_metrics/accessing-monitoring-apis-by-using-the-cli)

## Query contract and attribution

The frontend passes a captured connection generation, native source ID, core/v1 ResourceRef including UID, fixed range preset and, for a Pod, one currently declared container name. Default to the first application container, with a labelled selector when multiple containers exist. Show per-container history within Pod detail; individual containers have different lifetimes and coverage. Node detail shows node-wide root cgroup usage. Absolute units only. Current request/limit/allocatable values are unsuitable historical denominators.

Native code validates scope and named core GET access on the owned connection before provider I/O, checks UID and creation time, validates container membership, and rechecks the live identity/access before returning data. Retire results on any denial, source change, mismatch or disconnect. Metric series often lack resource UIDs: label the charts “Matched by source labels and current object lifetime.” Reject conflicting UID labels if supplied. Name-based results cannot establish container runtime identity or prove the source belongs to a cluster.

| Target | Required exact selector labels for every expression |
| --- | --- |
| Pod container | namespace, pod and container from the verified target |
| Node root cgroup | node from the verified Node name and id equal to / |

CPU uses `rate(container_cpu_usage_seconds_total{…}[5m])` in cores, converted to millicores. Require the total CPU series (`cpu="total"` or absent label for an unsplit counter); per-CPU variants are unsupported. Memory uses `container_memory_working_set_bytes{…}` in binary units. For each metric accept at most one matching physical series across the interval. Label ambiguity, duplicate replicas, restarted-container series or unsupported schemas can make a metric unavailable. Do not sum or silently pick one. Build matchers with string-literal quoting and URL encoding in Go. No arbitrary names for metrics or labels, queries, paths, offsets, raw response inspection or provider enumeration in the bridge.

Use GET /api/v1/query_range with a single UTC end time at request start. Presets are 1 h at 30 s (default), 6 h at 2 min and 24 h at 5 min. Snap end down to the step. Keep evaluation timestamps on that grid. Exclude points for which the underlying evidence could predate creation. CPU needs the full five-minute rate window; bound gauge lookback explicitly to at most five minutes, e.g. use last_over_time with a fixed five-minute input window. Apply the same lower bound on evaluation time for both. A young resource can have an entirely empty eligible range. The memory gauge can repeat its last sample within that window. An absent evaluation beyond the window leaves a gap. Show the requested range and actual coverage, with the warm-up explained. [Prometheus range API](https://prometheus.io/docs/prometheus/latest/querying/api/) and [query evaluation semantics](https://prometheus.io/docs/prometheus/latest/querying/basics/)

## Limits and evidence

Run the two metric queries sequentially with a 10 s provider timeout each, a 25 s total native deadline and two active history reads app-wide. Reject excess work as busy with no backlog. Request a series limit of two to detect ambiguity and enforce it locally even when ignored. Cap each decoded HTTP body at 1 MiB before JSON parsing, at 289 ordered unique points per series and at 128 KiB for the projected bridge result. Cancel underlying requests on hide, collapse, tab/target/container/range/source changes and disconnect. Manual refresh replaces the active read. Retain no charts on disk and run no background history timer.

Validate success envelope, matrix shape, exact scope labels, bounds, timestamp grid and finite nonnegative values. Missing or non-finite values leave visible gaps. Reject malformed/out-of-range/oversized results with a classified error. Keep real zero. Handle CPU and memory independently except authorization/identity failures, which clear both. Warnings or partial provider results visibly qualify the affected chart, using safe local wording. Distinguish unconfigured, missing series, ambiguous series, permission denied, unsupported response, capacity, timeout and transport failure. Never expose raw backend error bodies.

Show host, connection, target/container, range with timezone, step, CPU rate window, fetched time and last returned evaluation time for each metric. A range evaluation timestamp does not prove the time of the underlying scrape. Mark trailing coverage stale when the last available evaluation is more than two steps before requested end; label the snapshot with its fetch time even as it ages, and show that scrape freshness is unknown unless separately evidenced. On refresh failure clear the failed chart. Use separate labelled CPU and memory charts with gaps, keyboard-operable controls and an accessible equivalent listing timestamps, values and gaps. Reuse approved compact detail styles and theme tokens. No dashboard, new navigation group, charting dependency, alerts, AI input or node administration.

## Acceptance

- An operator can configure, change, remove or rediscover a source, select a container/range, refresh and explain the chart units, scope and coverage from the Overview alone.
- Independent provider and Kubernetes denials, name reuse, same names on two connections, credential replacement and a late response can never reveal obsolete history. A forged history request cannot send a provider token elsewhere.
- Valid zero, gaps, stale coverage, partial results and duplicate series remain distinguishable. Node evidence requires a node-labelled root series. Prove CPU counter reset handling and gauge semantics on a real Prometheus query engine.
- Use synthetic evidence and the approved kind contexts. Validate the Red Hat route/tenancy HTTP contract with deterministic tests; describe live OpenShift coverage only if separately authorized and actually performed. Verify cancellation and access controls with the packaged desktop app and record actual limitations. See the [implementation plan](../plans/2026-11-21-phase-1e4-historical-metrics.md).
