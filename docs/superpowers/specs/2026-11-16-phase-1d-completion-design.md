# Phase 1D completion — Manifest creation and server-side apply

Planning only; implementation occurs in separate sessions. Owners: [roadmap](../../roadmap/roadmap.html#phase-1d), [approved YAML-editing design](2026-11-16-phase-1d4-reviewed-yaml-editing-design.md), [security](../../security/security-model.html), [UX](../../ux/workflows.html), [verification](../../engineering/engineering.html#agent-verification).

## Scope audit and increment order

1D.1–1D.6 cover scaling, restart, deletion, editing existing YAML, retained workload history/rollback, Pod terminals and Pod/Service TCP forwarding. Their reports remain the evidence for actual environments and limitations. The missing committed capability is creating resources and applying declarative configuration with server-side field ownership.

Complete this in two increments, each with its own implementation PR and verification:

- **1D.7 — Named resource creation and bindings layout.** First normalize generated project bindings to `frontend/bindings/internal`, then deliver one YAML object, discovered route/scope, server dry-run, ordinary review/confirm, one POST that cannot overwrite an existing object.
- **1D.8 — Server-side apply and closure.** Explicit SSA of one existing resource, field ownership and conflicts, optional deliberate takeover in the same review, conditional submission, plus a consolidated Phase 1D exit audit.

Creation and apply are distinct actions, not a silent upsert. Existing Edit YAML stays conditional JSON Patch; it must not silently become SSA. This split lets the first increment ship independently and makes create-versus-update intent visible.

The bounded Phase 1D scope is single-resource operations. Multi-document/bulk import, generateName workflows, prune/apply sets, arbitrary subresource operations, automatic rebase/retry, laptop/local shell terminals and release/distribution work are explicit exclusions. Local terminals were already excluded by the roadmap; they are not an unfinished 1D obligation. Helm, metrics and node administration belong to 1E; OpenShift-specific workflows remain later even though installed custom resources can use generic YAML operations. No parity claim or all-provider verification follows from Phase 1D closure.

## Shared product and permission contract

Carry forward the user's approved 1D.4 simplification: Kubernetes decides authorization. Support advertised built-in, CRD/custom, namespaced and cluster-scoped resources, including Secrets, RBAC and storage, without a local kind allowlist or extra kind-based approvals. Scope/identity/format checks are not a substitute authorization system. Unknown permission hints do not block an otherwise server-authorized request. Actual API responses and advertised operation support govern availability.

Use the existing editor, diff/review modal, draft retention, operation coordinator and result UI. Preserve collapsible sidebar group state and the normalized bindings/internal generation pipeline. A submitted editor draft stays suspended until its result; late acceptance must not clear newer text, and uncertainty must retain the unchanged submitted configuration. Accepted resource navigation and refresh must support the selected exact API version with Get permission even where List is unavailable; never replace target identity or disclose Secret content outside deliberate reveal/edit. One normal review and Confirm; no typed-name or repeated Secret reveal gates for these YAML actions. Server admission additions/defaults and warnings appear in the same review. Preserve 1D.1–1D.6 actions and the resource inspector; no redesign or new editor framework.

Parse natively with the current lossless YAML parser, one object, unique string keys, exact unknown fields/numbers, no aliases/custom tags/templates/external references. Reject YAML streams, arrays and wrapper Lists with a clear single-resource message. Bound documents, prepared payloads and serialized review output to the existing 2 MiB limit; do not truncate reviews. Server response cap remains 16 MiB, warnings 8 KiB and requests 30 seconds. Reuse aggregate draft/review/result/concurrency limits; do not double budgets per action.

Drafts and values remain memory-only, never in settings/logs/retained results/AI. Explicitly opened Secret content is visible in editor/review and copy is user-initiated. Reuse native stringData→data normalization with stringData precedence; use standard base64 data on the wire for creation and SSA, because stringData is not a durable SSA field. No masked placeholders in submitted objects. Closing/discarding clears application references, not a promise of physical memory zeroization. Sanitized detailed server feedback may be displayed transiently in this editor, not persisted in operation history.

## Included maintenance — Generated bindings layout

The user explicitly requested that KubeSift-owned TypeScript bindings live at `frontend/bindings/internal/...`, removing the filesystem prefix `github.com/sandjaie/KubeSift/`. Include this as the first task of 1D.7; 1D.8 uses the normalized layout. This changes generated artifact paths and imports, not Go module/package names, public backend contracts, generated runtime binding IDs or application behavior.

The pinned Wails CLI exposes an output directory flag but no package-prefix-remapping flag. Its output mirrors Go import paths, and generated framework event declarations refer back into KubeSift model files. Use one deterministic generation pipeline: generate to an owned temporary staging directory, normalize only this repository's module-prefix paths, rebase relative module references throughout the generated tree, add existing source descriptions, validate the resulting tree, then publish it to frontend/bindings. Keep framework/third-party namespaces and the top-level events entry point distinct; do not flatten all packages into one internal directory. Reject output collisions or unresolved imports, and preserve existing output if generation/normalization fails.

Use the existing TypeScript parser/compiler dependency to identify actual module specifiers (imports, side-effect imports, re-exports and import-type expressions), including .d.ts and .js-suffixed references. Do not globally replace strings: Go binding identifiers, runtime calls, comments and unrelated literal values are not path aliases. Rewrite references by resolving their old source/target file locations and calculating relative paths after relocation. Update handwritten imports and test mocks to the new public path, remove the obsolete KubeSift-prefixed generated tree, and keep generation as the sole source of those files.

`wails3 task bindings`, npm bindings and all build/package dependencies must use this same pipeline. Verify two successive regenerations are identical, no old project-prefix import remains, source descriptions still pass, frontend typecheck/tests/lint/build succeed and packaged calls plus a generated session event work. Do not move folders manually after every build or change go.mod to influence frontend layout. This maintenance is delivered with 1D.7 and included in its whole-PR review, not an extra review gate.

## Native route and lock contract

Resolve apiVersion/kind through native discovery for the frozen connection generation. Map to exact group/version/resource and scope, with no plural guessing, arbitrary URLs or subresources. If more than one route matches, require explicit resource selection; stale/removed discovery requires a new review. Select requested API version explicitly, no fallback that rewrites the manifest. Creation requires advertised create; SSA requires get and patch. A create-only credential must not be forced to have get/list permission as a KubeSift policy.

Use the selected namespace as an explicit draft target. A missing metadata.namespace can be filled from it and shown in the normalized document before review. A differing manifest namespace must be reconciled explicitly in the editor/target selector before preparation; never silently move the request. Cluster-scoped objects have no namespace and the UI states Cluster scope. Selecting a resource type may offer a minimal identity-only skeleton; never initialize a create/apply draft by blindly copying server-generated fields from an existing object.

Extend coordinator locking to a canonical address key: connection/generation, API group/resource, namespace, name. Exclude version and UID from the lock key so create (no UID yet), apply, edit, scale, restart, delete and rollback cannot dispatch concurrently against the same address inside this app. Retain UID/version validation for existing-object actions as separate safety checks. Existing dedicated routes must canonicalize to the same key as discovery routes. No hierarchy/global cluster lock or claim that external clients are serialized.

Tokens bind action, draft revision, route/scope/name, payload, connection generation, API mode and any manager/force settings. Changing any of these invalidates review. Native operation ownership, five-minute review expiry, shared 128 draft/review records, 16 prepares, four executions, 100 terminal summaries and ten-minute duplicate-token lookup remain bounded. Wrong-action tokens cannot consume/reveal another action. Navigation retains unsaved drafts with the existing discard warning, but invalidates prepared submissions when identity/generation changes. No automatic resubmission after reconnect or uncertain write.

## 1D.7 — Create resource

Entry point: **Create resource…** in the resource inventory toolbar for the active cluster. It opens an in-memory YAML draft with frozen cluster and explicit namespace/cluster scope. It must work even when no existing object is selected. No automatic creation of a namespace, CRD, controller or supporting infrastructure; API absence produces an explanatory error.

Require explicit metadata.name. Reject generateName, UID, resourceVersion, managedFields, creationTimestamp, deletionTimestamp, deletionGracePeriodSeconds, generation, selfLink and top-level status in a create document with actionable validation, rather than silently dropping them. Labels, annotations, ownerReferences and finalizers are ordinary user-supplied configuration subject to server validation, not a local policy block. No requirement to read the requested name before create: POST/AlreadyExists is the atomic server boundary.

Prepare performs a single dry-run POST to the advertised collection with `dryRun=All`, `fieldManager=kubesift-create` and `fieldValidation=Strict`. Unsupported dry-run/strict validation returns a clear limitation without fallback. Proposed YAML and the admitted/defaulted server preview appear in the same review; exclude server-generated UID/version/timestamps/managedFields/status from the editable/proposed body and label preview-only generated metadata. Do not let users mistake simulated UID/default allocations for the eventual object's identity. Validate response GVK/name/namespace against the route and sanitize feedback. Secret preview remains in the deliberate editor only.

Confirm sends precisely the normalized proposed document, with the same manager/validation settings and dryRun removed, once. Do not POST the dry-run response: defaults/admission allocations can differ at execution. The token binds explicit name; a conflict/AlreadyExists is Rejected with “resource already exists”, never automatically Edit/Apply/Delete. An existing object appearing between preview and execution must remain untouched.

Successful creation is HTTP 201 with a valid matching returned object and nonempty UID/resourceVersion. Bind the result to that real UID, never the simulated one. A malformed/oversize success or lost response is Unknown, not failed-and-retry. No automatic retry, even if a subsequent GET is 404. Operation results store only address, actual UID if known, action and outcome, never manifest/Secret data.

After valid success offer Open resource using the returned identity; missing get permission does not change accepted creation into failure. After Unknown, **Inspect name** may perform a bounded explicit GET when allowed, but shows existence as an observation without adopting an object's UID as proof this request created it. No automatic operation against a possibly unrelated same-name object. Retain the draft for deliberate user reconciliation, with the consumed review invalidated.

## 1D.8 — Apply configuration to an existing resource

Entry point: **Apply configuration…** in the existing YAML section, distinct from Edit YAML. Capture the selected object's full bounded baseline, UID/version, canonical route and native field-ownership evidence. This action intentionally requires a readable existing object. Creation is handled by Create resource; SSA must not recreate a deleted target or update a replacement.

Start from an identity-only configuration (apiVersion, kind, name, namespace where applicable) and let the user paste/write desired fields. Show the existing captured resource as reference without defaulting the entire live object into the apply payload: submitting every live field can unintentionally claim ownership. A bare identity-only apply is valid but may remove fields previously owned by this manager; never treat it as a harmless no-op without server preview. No silent reconstruction of last-applied configuration from managedFields, and no local persistent last-applied documents.

Use stable field manager `kubesift-apply`, shown in review and not editable in this increment. It represents this application workflow across devices, not a person or authorization boundary. Creation uses the distinct `kubesift-create` manager; changing fields owned by that manager can conflict and is handled like any other ownership conflict. Applying an unchanged value may acquire shared ownership; unchanged visible values alone are not grounds to skip an SSA operation.

Native code injects the captured metadata.uid and resourceVersion into the wire payload as concurrency guards, separately from the editable desired configuration; reject user-supplied mismatching guards and reject managedFields/status/server-generated metadata. Route/name/namespace/API identity cannot change in an apply draft. Preserve user-specified optional field absence versus null and list contents; do not replace/merge arrays locally to emulate SSA. Kubernetes schema determines atomic/map/set list behavior. Omitting previously owned fields can delete/reset them; fields owned by other managers can remain. Preview comes from the API, not the existing JSON Patch diff engine's merge semantics.

Prepare sends PATCH `application/apply-patch+yaml` with fieldManager kubesift-apply, fieldValidation Strict, dryRun All and force absent/false initially. Use lossless normalized YAML/JSON-as-YAML bytes, not the whole baseline. Review shows desired configuration, full baseline→server-preview value diff, and a bounded ownership-change summary for kubesift-apply. Native managedFields evidence may be inspected transiently; do not submit managedFields or retain it in results. Display manager names/field paths as escaped bounded text and label truncated ownership evidence. Never expose credential/body text in retained errors.

Ownership conflicts are different from stale UID/version conflicts. Display safe manager/path evidence from structured conflict causes when provided. Offer **Take over conflicting fields** only as an explicit toggle within this same review flow, explaining that ownership changes and other controllers may change values again. Selecting it invalidates review and reruns dry-run with force=true. No automatic force, no additional kind approval wizard. Do not offer force for stale identity/version, Forbidden, immutable fields or arbitrary 409 responses that do not identify ownership conflicts. A fresh review after failure resets force to false; any changed configuration/baseline must reset it as well. The token binds the exact force choice and manager.

Execute revalidates current UID/version and sends the exact prepared apply payload once, with dryRun removed and no other option change. Keep both guards in the actual PATCH to protect the race after GET. Real-server tests must establish stale version and same-name replacement protection, including the delete-after-GET case: a deleted target must not be recreated by SSA. If any supported endpoint fails these preconditions, report that API limitation; never substitute unconditional SSA or silently fall back to JSON Patch. Do not consider Phase 1D.8 delivered unless representative built-in and custom API-server fixtures prove this boundary.

A successful update is HTTP 200 with matching identity and valid resourceVersion. HTTP 201 is unexpected for this existing-object action: record Unknown with a safe diagnostic and no follow-up mutation, and treat it as a delivery-blocking safety failure in verification. Valid success with later admission differences is Accepted with observed differences available in the current editor; do not automatically reapply or roll back. API acceptance does not establish workload readiness. Retained results contain action/target/manager/force-used/outcome only, not desired configuration or field values.

## Verification and closure criteria

Use small representative tests rather than a per-kind policy matrix. On explicit kind-dev-local-a/b, task-owned synthetic fixtures cover namespaced ConfigMap/workload, Secret stringData, one cluster-scoped resource and one already-installed custom API fixture. Synthetic CRD fixtures are test-owned and cleaned; no product-installed infrastructure. Verify actual server denial, create-only access, AlreadyExists race/no overwrite, dry-run non-persistence, unknown-response no replay, SSA ownership conflict/explicit takeover, omission semantics, unchanged-value ownership, same-name recreation and late resourceVersion races. Compare real managedFields for ownership behavior; HTTP fakes alone cannot prove SSA.

Parser tests cover duplicate keys, precision, unknown fields, bounds and malicious tags. Transport tests count actual create/apply HTTP dispatches on timeout/429/5xx/redirect/auth/bridge loss, including dry-run separately. UI tests prove draft identity retention, force reset and review invalidation, no secret spill, late replies, shared results and preserved existing edit/session behavior. Packaged computer-use verifies each new end-to-end flow and actual permission/conflict/Secret journeys; record actual platform/provider coverage and gaps. No duplicate user UAT checklist.

Each increment gets its own validation report and one independent whole-PR review/fix recheck, then ready-PR merge under existing policy. Implement 1D.7 first, then rebase the 1D.8 plan against that delivered code. No release or 1E implementation is implied.

The final 1D.8 task writes `docs/superpowers/validation/phase-1d-closure.html` with a concise evidence matrix for all eight increments: spec, merged implementation, representative automated/integration/native evidence, known limits and blocker/non-blocker classification. Verify that relevant plans have no unexplained incomplete tasks; distinguish approved exclusions from missing required behavior. Carry stream UID-race/remote-child-exit/throughput limitations and provider coverage limits from 1D.6 explicitly. Do not rerun every historical test without a change/risk reason; run focused combined regressions for shared coordinator/editor/transport/session behavior. Any material unmet committed acceptance criterion blocks the completion claim.

Only after creation and SSA are merged, reviews pass and closure has no unresolved blocker may the checkpoint say **Phase 1D complete for its specified scope** and identify 1E as next. Roadmap records scope/order/exit criteria only. This is not a release-readiness, every-Kubernetes-feature, every-platform or durable-audit claim. Update the capability inventory's stale Secret statement to reflect explicit reveal/edit already delivered, while keeping default browsing metadata-only.
