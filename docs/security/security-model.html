Security and AI data handling

Local-first operation with explicit targets, trusted helpers and controlled evidence sharing.

Assets and trust boundaries

Protect kubeconfig credentials, cloud sessions, provider keys, resource data and cluster integrity. Boundaries: untrusted cluster content → webview; webview → native services; kubeconfig → executable helpers; app → Kubernetes/monitoring APIs; evidence → external model; local project → public repository. A compromised laptop or malicious native dependency is outside a complete protection guarantee.

Threat Required control
Wrong-cluster changes Backend-bound connection generation, resource identity and operation payload; target shown during review
Untrusted kubeconfig executes code Review helper executable configuration before execution; no generic frontend shell API
Malicious logs/YAML/annotations Render as data, never active HTML or instructions; constrain navigation and native bindings
Credential or sensitive-data leakage Credential store, redaction, export review and no secrets in public fixtures
Expensive streams/queries Bounded queues, concurrency, timeouts, cancellation and visible truncation
AI prompt injection or unauthorized action Separate read-only tool surface, scope validation and evidence treated as untrusted data

Credential-helper trust

Review the resolved executable, arguments, kubeconfig source and configured environment overrides before the first run. Remember approval; prompt again when executable configuration changes. Resolve paths before matching trust so a PATH change cannot silently select a different executable. Store sensitive trust inputs as protected fingerprints where possible; redact displayed values.

Settings must list and revoke trusted entries. Revocation blocks future executions, not already-issued credentials. Proposed baseline: a routine binary upgrade at the same path does not count as configuration change; executable integrity checking can be evaluated separately. This trust mechanism is not a sandbox for an approved helper. Never execute a helper merely to preview an untrusted kubeconfig.

RBAC and mutations

Use permission checks to guide UI, but server authorization is final and can change between review and execution. Scope checks and target binding belong in Go, not only disabled buttons. An unrestricted credential remains powerful even if the UI is read-only.

  • Prepared operations bind connection generation, target, payload and relevant resource version/UID. Proposed confirmation records expire and are single-use; stale targets require renewed review.
  • Show differences for YAML changes and explicit impact for destructive actions. Production labels strengthen confirmation but do not replace normal controls.
  • Drain uses eviction semantics and respects disruption budgets by default. Never silently force-delete, bypass PDBs or discard local data; define exceptional options separately.
  • Helm installs/upgrades/rollback can execute hooks and modify cluster-scoped resources. Display the best available impact preview, explain incomplete previews, and require deliberate confirmation. Do not log sensitive values.
  • Operator lifecycle actions may create CRDs, cluster roles and resources beyond a namespace. Namespace access alone is not authorization for cluster-wide tests.
  • Container exec grants an interactive session capable of writes. Label its target clearly; do not describe it as read-only or promise confirmation for each shell command.

AI availability and provider routing

AI investigation is available in Phase 2. Application default provider plus per-cluster overrides references profiles stored securely. Show effective cluster/provider/model before submission. A missing or invalid override fails clearly; never silently fall back to another provider.

Claude is the first adapter. OpenAI API, OpenRouter and other supported providers follow a provider abstraction; arbitrary API keys and consumer subscriptions do not imply compatible APIs or model capabilities.

Configuration read boundary

Planned Phase 1C.3c permits ConfigMap inspection and strictly metadata-only Secret browsing. Secret requests must not fall back to full objects, and arbitrary metadata such as last-applied annotations must not cross the desktop bridge. Secret value reveal, YAML and Events are outside this increment; generic readers must not bypass that boundary. Metadata-only requests still need ordinary Secret permissions. ConfigMap content and metadata can contain sensitive text; keep captures local and ephemeral, out of logs, telemetry and AI submissions.

Evidence and tool contracts

Collect only bounded, relevant evidence. Exclude credentials and Kubernetes Secret values from model submissions; logs, annotations, Helm values and ConfigMaps can also contain secrets. Redaction is defense in depth, not a guarantee. Explicit sharing policies and payload review govern sensitive logs/configuration; policies can be remembered to avoid repetitive prompts.

Proposed read-only tool Constraints
Inspect workload / related events Connection and resource scope, field allowlist, collection time and source references
Get relevant logs Container, time/line/byte limits, redaction and sharing policy
Get resource metrics / history Selected endpoint, approved templates, bounded range/step/series/timeouts

Do not initially expose arbitrary shell, mutation, URL-fetch or unrestricted PromQL tools. Kubernetes RBAC does not automatically enforce namespace access on a shared Prometheus endpoint; provider-side access controls and application query scope require separate validation. Keep raw evidence local by default; send only the permitted projection.

AI output distinguishes observations from hypotheses, cites evidence and time windows, acknowledges missing data and does not assert a memory leak solely from increasing memory. Phase 2 has no AI write tools. Future remediation needs a separate design.

Audit, persistence and public-source hygiene

Proposed local audit records: action type, target reference, time, outcome, confirmation and provider profile identifier where relevant. Never record credentials, full log payloads or Secret values. Retention/deletion settings must be chosen before release. Investigation history persistence is opt-in and needs a separate storage review.

Use synthetic fixtures and exclude credentials from tracked files. Exports and issue reports require preview. Diagnostic uploads and telemetry are not enabled by this plan.

Development boundaries

Use disposable local clusters for destructive tests. External integration tests require explicit targets and allowed actions. Real-provider tests must not print credentials. OpenShift lifecycle and node maintenance need suitable isolated environments. The app itself deploys no supporting agents or monitoring components.
